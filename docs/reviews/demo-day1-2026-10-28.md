## 5. Drift and day-one findings

**Runbook §6/§7 expectations vs observed:**

1. **`APP_URL` was not moved to the demo domain** (runbook §6 step 1 said set
   `"APP_URL": "https://cf-gitea-demo.aiapp.run"`). As-built, the real config
   keeps `APP_URL = https://cf-gitea.hecongw.workers.dev` with a deliberate
   comment — "Keep BOTH surfaces: defining routes would otherwise disable the
   workers.dev subdomain — APP_URL + the README's live link ride it". Given
   the brief's confirmed design (both surfaces demo-armed), pointing
   `APP_URL` at one surface over the other is a coin the config comments
   resolve toward workers.dev; recorded as accepted divergence, not drift to
   fix. Consequence: absolute links minted from `APP_URL` (e.g. the quota
   403's `"url"` field above) name the workers.dev origin even on the demo
   surface — cosmetic, upstream's swagger URL field behaves the same way.
2. **The brief's "the demo had ~0 users at flip" is wrong for THIS instance:**
   the flip did not start from empty — it re-armed the RD-era production
   worker in place, inheriting 4 users / 2 repos (§2). SPEC §6.4's guidance
   ("flip on a fresh instance, or expect the backlog sweep") was satisfied
   only because the inherited set happened to contain no non-admin repo
   older than 72 h (`p0probe/p0-shallow` is 90.4 h old but admin-exempt).
   An operator flipping a USED instance should not count on that luck; the
   §6.4 backlog-drain note stands.
3. **FINDING (new, SPEC §3.1 gap): a dangling `owner_id` escapes the sweep's
   fail-safe.** `dp3t/p0-shallow` carries `owner_id=55` with NO users row 55
   (the account was evidently hand-removed from D1 pre-day-one without the
   user-delete cascade — its `action` row survives too, §4). The producer's
   `LEFT JOIN users` + `or(isNull(ownerId), eq(users.isAdmin, false))`
   matches neither arm for a dangling id (ownerId not NULL; `isAdmin` reads
   NULL), so this repo will NEVER be swept — it crosses 72 h tomorrow and
   stays. The SPEC documented the NULL-owner fail-safe ("no exempting
   principal exists → swept") but the dangling-id state slips between the
   documented arms. One-line fix shape: `isNull(ownerId) OR users.id IS NULL
   OR users.isAdmin = false`. Small, real, and now visible on day one.
4. **Day-one observation of the `SQLITE_LOCKED` retry class — on production,
   fully absorbed.** During the five same-second delete cascades the tail
   captured 29 exception-outcome events, ALL `Error: database table is
   locked: SQLITE_LOCKED`, in two bursts (14:53:52–56, 14:55:23–45 UTC) with
   ~0.5–1.5 s redelivery spacing — the queue consumer's throw-and-retry
   contract working (`max_retries: 5`). End state clean: all five repos
   purged, zero leftovers, no DLQ entry (`repo-tasks-dlq` stays with 0
   producers). This is the e2e-sweep's storage-layer finding
   (`docs/reviews/e2e-sweep-2026-10-28.md:320-355`) seen in production
   burst form; the M0 DLQ would have made any actual drop visible. No
   action demanded today; worth watching if delete bursts grow.
5. **Intermittent TLS handshake resets on the custom domain from this
   vantage** (`curl: (35) OpenSSL SSL_connect: SSL_ERROR_SYSCALL`): two
   windows (~14:49–14:52, ~14:54–14:57 UTC) in which a fraction of
   connections to `cf-gitea-demo.aiapp.run` died mid-handshake while
   `cf-gitea.hecongw.workers.dev` answered fine; between windows 8/8
   healthz probes passed. Pattern (custom domain fails, workers.dev clean,
   self-recovers) reads as environmental path interference on the
   `.aiapp.run` SNI from this network, not worker behavior — the runbook's
   cert-provisioning branch does not apply (the cert landed at the freeze).
   Recorded for the next operator: retry-on-000 before diagnosing; probe
   the workers.dev twin to split path-vs-instance.
6. **SPEC-0014 §6 edge cases day-one can already show:** §6.2 (admin
   exemption) — LIVE: the 90.4 h-old `p0probe/p0-shallow` survived five
   sweep ticks by exemption, not by accident; §6.8 (strict `"true"` gate) —
   the config carries the exact string and the tick log exists, so the
   armed arm is proven end-to-end; §6.4 (pre-flip rows) — exercised by the
   inherited fixture, exempted correctly; §6.6/§6.7 (raced delete, double
   enqueue) — no messages day-one, nothing to observe; §6.9 (last repo
   swept under an active session) — not yet observable. The remaining
   edge cases need an aged non-admin repo, which day-one cannot produce
