```

FAIL: empty-pack branch create (tip already known) (got '1' want '0')
```

Root cause chain, with evidence:

1. The setup's clean-slate `DELETE $BASE/demo` (`e2e.sh:54`) did not wipe the
   `demo/demo` cell left by the 2026-10-26 sweep's own run. The engine-shape
   DELETE of a D1-resolved repo runs the sanctioned §2.5.5 pipeline
   (`apps/worker/src/git-http/gate.ts:637` →
   `apps/worker/src/repos/purge.ts:253` `deleteRepositoryViaEngineShape`: D1
   cascade FIRST, then tombstone, then the REPO_TASKS queue purge whose final
   `destroy()` is the only cell wipe — `purge.ts:106-116`). The D1 row IS gone
   today (verified: `SELECT … WHERE owner_namespace='demo'` returns `[]`), so
   the pipeline ran; the async cell wipe did not.
2. The suite re-pushes ~1 s later into the still-stale cell. Git rejected all
   three refs (quoted verbatim from the run log): `! [rejected] main -> main
   (fetch first)`, `! [rejected] lightweight-tag -> lightweight-tag (already
   exists)`, `! [rejected] v1.0 -> v1.0 (already exists)`. Everything
   downstream cascades: the clone served the previous run's 9-commit history
   (`unshallow = full history (got '9' want '8')` — the stale tip count
   matches the previous run's final main exactly), the incremental-fetch
   section's push failed again, and the empty-pack create hit a stale
   `empty-pack` ref.
3. The queue purge for the cell failed with `SQLITE_LOCKED` (see the
   storage-layer section below) and after `max_retries: 5` was DROPPED — the
   repo-tasks consumer has no DLQ yet (`wrangler.jsonc:131-137`: "after
   max_retries the message is dropped"). The cell survived as an orphan
   serving stale refs under a name whose D1 row was gone.
4. Corroborating evidence from the SAME run: section 13's DELETE of
   `demo/private-repo` (200 + async purge, no racing traffic on that cell)
   wiped cleanly — the delete machinery works at HEAD when its destroy is not
   racing; the failure is specific to the cell whose purge window overlapped
   the suite's live receive/fetch/gc traffic.

The mid-run self-heal is also diagnostic: section 6's FORCE push overwrote
stale main (`ok: force push`, gc answered `{"removed":3,"kept":56}`), and
sections 6-7 then passed — the protocol itself never misbehaved; every one of

**The 4-failure diagnosis (deterministic, predates the fix wave):**

1. The suite's seed repo is created by `git push srcseed.git main feature` —
   BOTH branches in one receive-pack to a nonexistent repo. The push-create
   settle adopts the **alphabetically first** branch as `default_branch`
   (`gate.ts:1030-1038`; the code comment states the approximation honestly:
   "a multi-branch first push adopts the alphabetically first branch (upstream
   adopts the pushed branch; indistinguishable here without an engine hook)").
   `feature` < `main`, so the row lands `default_branch='feature'` (verified
   in D1 after the runs: `{"slug":"srcseed",…,"default_branch":"feature"}`).
2. The suite then deletes `feature` upstream (the prune scenario's
   precondition). SPEC-0013's push-time gate refuses deleting the default
   branch (`gate.ts:873`: `if (cmd.kind === "delete" && branch ===
   repo.defaultBranch)`), git shows `! [remote rejected] feature (Branch
   feature is the default branch and cannot be deleted)`, and checks 2-4
   cascade (the ref never disappears → prune-on "still advertised"; the
   recreate push is then a plain non-fast-forward against the surviving tip;
   the prune-off survival check fails on the same unfinished precondition).
   Run C's mechanism is pure rejection semantics — no 500s involved.
3. **Regression classification: NOT a fix-wave regression.** The
   alphabetically-first adoption landed `f052c64` (2026-10-24, SPEC-0003
   M2/M3; the fix-wave commit `0626ced` of 10-28 07:35 only firmed
   `branches[0]?.` into `branches[0]!.` on the same line — no behavior
   change). The default-branch delete gate landed `d7fdc49` (2026-10-25
   18:22, SPEC-0013 M2). The mirror suite itself landed `a38f92e` at
   2026-10-25 **07:55 — sixteen hours BEFORE the gate** — so the suite has
   never run green against the gate; there is no prior green record this
   could be a regression FROM. The failure is fully deterministic at HEAD
   (reproduced identically in runs A and C), not flaky.

**Verdict: RED, 77/4 — a deterministic suite-vs-product interaction that
predates the fix wave.** Resolving it is a decision, not a fix: either the
harness stops exercising the approximation (single-branch first push, or
delete a NON-default branch), or the product's default-branch adoption moves
to upstream's pushed-branch/HEAD semantics (note the engine's own first-push
adoption already prefers main/master — `gate.ts:1058-1060` documents that the
DO head can diverge from the D1 settle's pick, and `setHead` re-points it to
the alphabetically-first name, compounding the divergence). Follow-up unit's
call; not done here.

**RESOLUTION (2026-10-28, mirror-HEAD-adoption unit — product fix, not
harness):** the adoption rule moved to HEAD-first per upstream. Upstream pins:
a mirror follows the SOURCE's advertised HEAD (the migration clone is
`git clone --mirror`, whose HEAD IS the source's, read back by
`GetDefaultBranch` — `services/repository/migrate.go:135-145`); the mirror
population settle `checkAndUpdateEmptyRepository` (`mirror_pull.go:419-474`)
prefers the row's default → master → main → first result and calls
`SetDefaultBranch` (symbolic-ref HEAD, `modules/git/branch.go:37-41`);
push-create `pushNewBranch` (`push.go:255-268`) adopts the first-pushed branch
op. As built now: `settleCreatingRepo` (`gate.ts`) adopts the engine's
recorded HEAD (the `commitPush` fixup `git/protocol.ts:1615-1623`: main →
master → first, applied over the whole command plan — the receive path's
honest stand-in for upstream's per-op order) when it names a landed branch,
alphabetical-first kept as the HEAD-less/unborn fallback (the setHead
alignment now only fires on that fallback arm, so it no longer clobbers the
engine's pick); the mirror population settle (`sync.ts`
`settlePopulatedRepo`) adopts the source's ADVERTISED HEAD
(`advert.headSymref`, already parsed by `gitclient.ts` in both v0
`symref=HEAD:` and v2 `symref-target:` shapes) when it landed, then the
engine's recorded HEAD, then alphabetical — and aligns the DO head once at
that transition (upstream's `SetDefaultBranch` parity). The old rule's test
pin (`repos/lifecycle.test.ts` "aligns the DO head…") was re-pointed to the
new rule; SPEC-0003 §2.5.2 and SPEC-0009 §4.3.8 amended as-built. Witness:
`pnpm test:mirror` → `=== RESULT: 87 passed, 0 failed
(workdir /tmp/cgit-mirror-e2e.0wcabe) ===` exit 0, with section 7 all green
("ok: feature branch deleted upstream (both sides)", "ok: prune-on: deleted
ref pruned from the target", "ok: prune-off: recreated ref lands", "ok:
prune-off: upstream-deleted ref SURVIVES on the target"), plus
settle-pinning vitest suites 135/135, `pnpm typecheck` exit 0, eslint clean
on the touched files. (The suite count moved 81 → 87 between the sweep and

## Storage-layer finding — `SQLITE_LOCKED` on DO-cell wipes (environmental trigger, product-visible effect)

A cross-suite observation that the sweep's diagnosis kept running into,
reported because it silently poisons both suites' clean-slate DELETEs:

- Symptom: a RepoCell destroy answers `HTTP 500` with the raw driver text
  `database table is locked: SQLITE_LOCKED` in the body. The throw escapes
  the wipe's `storage.transactionSync` (`packages/git-engine/src/control-plane.ts:854-859`
  → `store.wipe()` at `src/git/store.ts:488`; the escaping error is from the
  wipe — destroy's own `removeFromRegistry` failures are caught and logged,
  and none of those log lines appeared). The same error surfaced once inside
  the §2.5.5 pipeline path (old-date-repo's pipeline DELETE 500'd; its bare
  destroy succeeded seconds later).
- Observed behaviors: (i) it can PERSIST for a specific cell file across full
  dev-server restarts (the sweep-day `demo/demo` refused every destroy for
  ~10 minutes across two restarts until the file was removed; the three
  re-created `demo/*` cells locked again the same way at sweep end); (ii) it
  is cell-specific, not server-wide — on the very same fresh server, the four
  `mirrore2e` cells all deleted 200 while the `demo` cells 500'd; (iii) it
  correlates with cells whose purge/receive activity overlapped worker
  restarts (vite HMR) or abrupt process kills — the sweep's own process
  hygiene contributed (a leftover dev-server pair from mirror run B was found
  still holding 5173 and the cell files; killing it was necessary but not
  sufficient for the then-newest cells).
- Consequences: (1) both suites' setup DELETEs discard the response
  (`e2e.sh:54-55`, `mirror-e2e.sh:205-207`), so a locked cell silently
  cascades into a whole-run failure storm (mirror run B: 17 failures from one
  stale cell); (2) a queue purge that hits the lock retries 5× and is DROPPED
  (no DLQ, `wrangler.jsonc:131-137`), leaving an orphaned cell serving stale
  refs under a name whose D1 row is gone — exactly the 29/40 engine excursion;
  (3) the raw driver error in the response body is upstream-parity noise
  (minor).
- Nothing fixed here (read-only unit). Repair used during the sweep: stop the
  server, remove the affected cell's SQLite file under the gitignored
  `apps/worker/.wrangler/state/v3/do/cf-gitea-RepoCell/`, restart — proven to
  fully clear the state (the clean engine re-run followed).

## Open issues for the orchestrator

1. **`pnpm test:mirror` cannot exit 0 at HEAD** — the section-7 prune
   scenario collides with the alphabetically-first default-branch adoption
   (`gate.ts:1030-1038`) behind SPEC-0013's delete gate (`gate.ts:873`).
   Deterministic, predates the fix wave (f052c64 10-24 + d7fdc49 10-25 18:22;
   suite a38f92e 10-25 07:55 never ran against the gate). Needs a decision:
   harness change (single-branch first push / delete a non-default branch) or
   product change (upstream's pushed-branch adoption; note the DO-head
   divergence documented at `gate.ts:1058-1066`).
2. **`SQLITE_LOCKED` wipe failures + silent purge drop** (section above): a
   wipe retry/backoff, a DLQ (or tombstone-era reaper) for dropped purge
   messages, and surfacing the suites' setup-DELETE status are the candidate
   follow-ups. Until then, a poisoned cell poisons whole suite runs silently.
3. **Suite hardening**: e2e.sh/mirror-e2e.sh setup DELETEs discard the
   response; the mirror suite's `next_sync_at` read races the settle (assert
   after settle, or tolerate `0` when `last_sync_at` is already set).
4. **Suites that own a `pnpm dev` server are vulnerable to concurrent source
   edits on the shared tree** (two of three mirror runs were hit by sibling
   HMR reloads, one by a PARSE_ERROR window). Fine in CI (quiet checkout);
   consider a worktree/scratch checkout for local runs during active waves.
5. Housekeeping carried over from the 2026-10-26 doc: the M3.5 count line in
   `specs/0011-compaction-gc.md` ("15 scripts / 260 checks") still predates
   `check-validate-push.mjs` (canonical: 16/269) — untouched here (outside
   this unit's ownership).
6. End state: no dev servers left running (ports 5173/5199/8443 free), no
   sweep processes alive; local dev scratch left tidy (the locked demo cells
   removed at the file level; `mirrore2e`/`lfse2e`/`demo` rows and cells
   purged or removed; `probeowner`/`sweeptidy` probe users deleted). The
   `.wrangler` state is gitignored dev scratch.
