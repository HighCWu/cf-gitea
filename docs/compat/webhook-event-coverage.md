# Webhook Event Coverage Audit — upstream pin vs. emitted

Audit date: 2026-10-24. Upstream pin: `gitea` submodule at `fc4936884584a41931906553d96c2601d750e6ef` (v1.22.0-rc1-3919-gfc49368845).

- **Canonical upstream list**: `HookEventType` enum, `gitea/modules/webhook/type.go:10-43`; the wire-relevant set is `AllEvents()` (26 types, `type.go:45-74`); `schedule`/`workflow_run`/`workflow_job` (`type.go:40-42`) are Actions-only. Payload shapes: `gitea/modules/structs/hook.go` (struct lines cited per row).
- **Our side**: `HookEventType` union + `webhookHasEvent` (`apps/worker/src/issues/webhooks.ts:25-49`, `:95-100` — port of `models/webhook/webhook.go:171-185`; already models the `pull_request_review` group flag of `type.go:38`); fan-out `emitWebhookDeliveries` (`webhooks.ts:177-236`).
- **Status vocabulary**: EMITTED (real events, all trigger paths) / EMITTED-PARTIAL (emitted from a subset of upstream's trigger paths or actions) / NOT-EMITTED (the feature exists, only the webhook is missing) / N/A (the triggering feature itself does not exist yet).
- Note: upstream has **no `tag_push` type** (that name is Gogs/GitLab vocabulary) — tag pushes arrive as `push` + `create`/`delete` on `refs/tags/*`, which our push-family builder already produces.

## Coverage ratio

Over the 26 wire event types of `AllEvents()` (`type.go:45-74`):

- **Fully emitted: 3/26** (`push`, `issues`, `pull_request`) — 12%.
- **At least partially emitted: 7/26** (the above plus `create`, `delete` — git paths only — and `issue_comment`, `pull_request_comment` — created action only) — **27%**.
- **NOT-EMITTED with the triggering feature already present: 9/26** — `fork`, `issue_label`, `issue_milestone`, `pull_request_label`, `pull_request_milestone`, `pull_request_sync`, `repository`, `release`, `status` (+ the `create`/`delete` API-seam gaps counted as partials above). These are webhook-only work: the emitting service (`emitWebhookDeliveries`) and subscription filtering (`webhookHasEvent`) already cover them.
- **N/A, feature absent: 10/26** — the three PR-review events + `pull_request_review_request`, `issue_assign`/`pull_request_assign` (assignees TODO, `api/services/issues.ts:226`), `wiki`, `package`, `workflow_run`, `workflow_job`.

## Recommended next wave (max 5, ranked by real-client expectations)

In-tree client evidence is limited (vendored `gitea/docs/` covers building only, no webhook consumer docs; the client-facing surface in-tree is the event-selection UI `gitea/templates/repo/settings/webhook/settings.tmpl:95-347` — every type below has a checkbox there — and the per-integration formatters `services/webhook/{slack,discord,dingtalk,telegram,packagist}.go`, which render payloads of exactly these families). Ranked:

1. **`release`** — feature exists end-to-end, zero emissions; the classic CI/deploy trigger (upstream ships a dedicated Packagist hook type, `services/webhook/packagist.go`, whose payloads are release events). One emit call per release route action closes it. P1 per definition.
2. **`issue_label` + `pull_request_label`** (one wave, two types) — label automation bots are the most common non-CI integration; the label routes landed with the emission explicitly deferred (`issue-write-t2.ts:77`), so the seam is owned and ready.
3. **`pull_request_sync`** — CI systems re-run checks when a PR head branch moves; upstream fires it from exactly the push path we already own (`notifier.go:835-845`), and `emitPushFamilyUpdates` already sees every applied ref delta (`webhooks-push.ts:252`). Small delta, high CI value.
4. **`repository` (+ `fork` while in the file)** — repo lifecycle events feed mirrors/backup/organization tooling; create/delete/migrate routes exist, fork task exists (`src/repos/fork-task.ts`); all four upstream actions map onto seams we landed.
5. **`status`** — commit-status consumers (status dashboards, gated-merge UIs) subscribe to exactly what our landed statuses routes already persist; only the emit call in the POST handler is missing.

Honorable mention (fold into any issues-family wave): comment `edited`/`deleted` emissions for `issue_comment`/`pull_request_comment` — the routes exist (`issues.ts:470/:491/:548-549/:569-570`), upstream emits (:476/:517), and comment-sync bots expect the full triple.
