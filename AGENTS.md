# AGENTS.md

Guidelines for AI coding agents working in this repository. Read this before making changes.

## Project Overview

**cf-gitea** re-implements Gitea's backend on Cloudflare's developer platform. The official Gitea web UI is the frontend; all backend hosting runs on Cloudflare Workers.

- **Frontend**: the official Gitea codebase, vendored as a git submodule at `gitea/` (upstream go-gitea/gitea, pinned commit). Treat it as a **read-only reference** — never modify files inside `gitea/`. Note: `gitea/AGENTS.md` is upstream's file for Go development and does **not** apply to this repository.
- **Backend**: Cloudflare Workers built with **Hono + TypeScript + Drizzle ORM + Durable Objects**.
- **Storage**: **D1** for relational metadata (users, orgs, repos, issues, PRs); **R2** for large blobs (git packs/objects, LFS, attachments); **Durable Objects** for per-repository coordination and write serialization. **Cloudflare Artifacts Beta** is an optional candidate store for git objects — evaluate it in a SPEC before adopting.
- The backend must remain API-compatible with the Gitea HTTP API the frontend expects, including the **git smart-HTTP protocol** (`/info/refs`, `git-upload-pack`, `git-receive-pack`) implemented on Workers against R2/DO storage.

**Language rule**: all code, comments, identifiers, commit messages, SPEC documents, and docs are written in **English**.

## Structure Rules

- Drizzle migrations live ONLY in `apps/worker/src/db/migrations` (drizzle-kit `out`
  and wrangler `migrations_dir` both point there).
- No placeholder files: every module contains its real implementation; scaffolding
  stubs are deleted, not committed.
- The vendored package keeps upstream's internal layout; every deviation is recorded
  in `packages/git-engine/NOTICE.md`; adapted scripts keep exactly one copy (e.g.
  `e2e/e2e.sh` — never duplicate upstream scripts into `scripts/`).
- `packages/**` is excluded from eslint and from consumers' strict type-checking;
  consumers see the engine through its generated declarations (`dist-types/`).
  Editing engine sources? `pnpm typecheck` regenerates the boundary automatically
  (pnpm -r runs the engine before the worker via the workspace dependency order).
- `wrangler.jsonc` is GITIGNORED and account-local (it carries the real resource
  ids); the COMMITTED `wrangler.jsonc.example` is the template. `pnpm
  setup:deploy` copies the example on first run, provisions D1/R2 if missing,
  fills the real id (comment-preserving single-line swap), then applies remote
  migrations; CI restores the file from the example right after checkout. This
  is the GRADUATED example-file model (gitorange's installer pattern), adopted
  2026-10-28 when the repo went public for third-party self-hosting — the
  earlier committed-placeholder state is history, do not revert it.
- Generated artifacts are never committed: `dist/`, `dist-types/`, `.wrangler/`,
  `worker-configuration.d.ts` (regenerate with `wrangler types`).

## Dependencies

- Keep dependencies at the **latest stable** versions; never pin alpha/beta/RC/next/
  canary dist-tags. Prefer majors over compat-holds.
- Intentional holds (record any new one here with its reason):
  - `pako ^2` — the vendored engine is written against the pako 2 API; pako 3 would
    force source edits (revisit at the M2 adaptation).
  - `@types/pako ^2` — latest 3.0.0 is a deprecated stub ("pako provides its own
    type definitions" — pako 3 only); moves with the pako hold, stays 2.0.4.
  - `typescript ~6.0.3` — typescript-eslint peer range caps at `<6.1.0`; bump with it.
  - `compatibility_date 2026-10-23` — newest date the pinned workerd/miniflare
    supports; raise it together with wrangler updates (see wrangler.jsonc comment).
  - `@cloudflare/workers-types ^5.20261025.1` — daily-types package kept at latest
    stable; each fresh version is younger than pnpm's release-age gate, so the
    upgrade adds a `minimumReleaseAgeExclude` entry to pnpm-workspace.yaml.
  - transitive `miniflare 5.20261023.0-beta` (+ `unenv 2.0.0-rc.24`,
    `youch 4.1.0-beta.10`) — upstream's coordinated EXACT pin inside
    wrangler/vite-plugin/vitest-plugin; no stable 5.x exists and forcing 4.x
    mismatches our compatibility_date's workerd. Dev-only, outside the
    no-prerelease rule's intent (our declared deps stay stable); revisit at
    miniflare 5 GA — analysis in docs/research/miniflare-beta-pin.md.
- pnpm 12 enforces a default release-age gate (`minimumReleaseAge`, unset in
  config) — a just-published version resolves as "already up to date" and a
  lockfile carrying it FAILS plain `pnpm install` (observed 2026-10-25: hono
  4.13.14, published that morning). Young upgrades simply wait; only packages
  needing day-one freshness (workers-types above) get an exclude entry.
- eslint lives at the ROOT only (flat config lints the whole repo); per-package lint
  scripts and eslint deps are forbidden.
- pnpm is the only package manager; `pnpm-lock.yaml` is committed.

## Commit Policy

- **Atomic commits**: one logical unit per commit — scaffold / vendored engine /
  one feature module / one docs+specs batch. The orchestrator commits a unit when
  its owning agent lands and gates are green; **agents never run git commit**.
- Never commit while a unit's agent is mid-flight (moving target); the landing
  review is the commit point. **Pre-commit checklist (hard-learned):** (1) see
  the actual `Tests ` line for the affected scope with your own eyes — never
  pattern-match or trust the agent's claim — and NEVER pipe the suite through
  grep in the same `&&` chain as the commit (the pipe's exit code masks
  vitest's failure; observed 2026-10-26: a 10-failed run committed under a
  "35/35" message); (2) `git status` the whole tree and
  diff every path your change touched — `git add` by directory silently misses
  sibling paths (two escaped commits this session); (3) after ANY concurrent
  edit window, re-verify your own change landed (grep/json.load) before
  committing — a rejected edit + a successful commit of a neighbor's change
  looks identical to success; (4) **git safety under concurrency** (the
  shared-index incident, 2026-10-25): commit ONLY via pathspec
  (`git commit -m "…" -- <your exact paths>`), NEVER reset/rebase/amend while
  sibling waves are in flight, and verify with `git show --stat HEAD` that
  only your paths landed — a sibling's staged files swept into your commit
  (or your commit referencing their untracked file) means STOP and escalate
  to the orchestrator, never attempt history surgery yourself; (5) `tsc
  --noEmit` is its own gate — vitest does not typecheck across files; (6) a
  path you legitimately own can still carry a sibling's uncommitted hunk
  (the admin-org-extras arity fix folded into 9f92950, 2026-10-26): before
  committing any file another agent may have touched, read
  `git diff HEAD -- <file>` hunk-by-hunk — every hunk must be yours or a
  disclosed integration; attribute an unknown hunk first (ask the pool /
  read the wave log), then fold it in deliberately and say so in the commit
  message, or re-edit to exclude it. (7) a JSON-file edit validates
  `python3 -m json.tool` (or json.load) IN THE SAME COMMAND as the commit —
  JSON has no comments, and an engines comment shipped broken once (aa9d5ba);
  (8) command chains never carry a bare newline into git — keep
  `git add … && git commit … -- paths` on one logical line (the same incident:
  the failed gate ran the commit+push anyway; cousins of (1)'s pipe-masking
  and (4)'s pathspec rules); (9) YAML workflow edits get the structural check —
  every `with:` rides a `uses:` (a cp-step insertion orphaned seven checkout
  with-blocks; the first public CI run died at PARSE — GitHub's parser is
  stricter than the PyYAML that passed it, validate locally beyond PyYAML)
  (62cb441).
- Generated artifacts stay out (see Structure Rules); `pnpm-lock.yaml` IS committed.
- **Submodule hygiene**: `gitea/` stays pristine — never run installs or builds
  inside it (asset builds run in scratch dirs, `scripts/build-gitea-assets.mjs`);
  if `gitea/pnpm-lock.yaml` ever shows modified, `git -C gitea checkout --` it.

## Parallel Agent Work

- Subagents are dispatched as **background** agents (`run_in_background`), never
  blocking the orchestrator; agents message the orchestrator when blocked, and the
  orchestrator integrates, reviews, and adjusts direction mid-flight.
- **Completion-loop discipline (user-mandated)**: after EVERY subagent
  completion — review, verify, commit, AND immediately dispatch a
  replacement to hold the pool at the target concurrency (**6**, unless the
  user has set a temporary throttle window — honor it and restore on its
  expiry). A landing that ends at the summary without a re-dispatch wastes
  the slot; keep a warm queue of dependency-ready unowned goals for exactly
  this moment.
- Every dispatched task declares **exclusive file ownership**; an agent must not
  create or modify files outside its ownership. Shared files (e.g. `src/index.ts`,
  root `package.json`, `wrangler.jsonc`) are touched ONLY by the orchestrator or by
  an explicitly designated owner — never by parallel agents simultaneously.
- Agents report: files touched, commands run with honest pass/fail, deviations from
  the brief, and open issues for the next wave.

## SPEC-First Workflow

Before implementing any non-trivial feature or fixing a design-level bug, write a SPEC in `specs/` (English, Markdown, kebab-case filename, e.g. `specs/git-smart-http.md`). A SPEC covers:

1. Problem and scope (what's in and out).
2. API surface, with notes on the corresponding upstream Gitea behavior.
3. Data model: D1 tables, R2 key layout, and/or Durable Object classes involved.
4. Edge cases, limits, and failure modes.
5. Testing plan.

Implementation follows the SPEC; if the design changes during implementation, update the SPEC in the same change. Trivial fixes (typos, small refactors) do not need a SPEC.

## Architecture Boundaries

- **Routes are thin**: Hono handlers only parse, validate, and respond. Business logic lives in service modules under `src/`.
- **D1 access goes through Drizzle ORM only** — no hand-written SQL strings in route handlers. Schema changes require a generated migration.
- **Blob storage goes through a storage service layer** (one interface over R2), so Cloudflare Artifacts Beta can be evaluated or swapped in without touching callers.
- **D1 is the source of truth for metadata; R2 is the source of truth for blobs; DOs serialize concurrent mutations** (e.g. per-repo git pushes). Do not duplicate state across them.
- **`wrangler.jsonc` is the single source of truth for bindings.** The Vite plugin reads it for local dev; never duplicate binding config elsewhere. After changing it, run `wrangler types` and never hand-write `Env`.
- **Never modify anything inside `gitea/`**, and never commit changes to the submodule pointer casually — the pin is deliberate.

## Workers Rules

- Keep `compatibility_date` current (use today's date for new Workers); review compat flags when bumping.
- Enable observability in `wrangler.jsonc`: `observability.enabled` and `observability.traces.enabled` are both `true`.
- **Stream large or unbounded bodies** (git packs, uploads). Never `await request.arrayBuffer()` / `.text()` on data of unknown size.
- Use `crypto.randomUUID()` / `crypto.getRandomValues()` for IDs and tokens — never `Math.random()`.
- Attach background work to `ctx.waitUntil(...)`; never fire-and-forget promises.
- No module-level mutable request state — pass request state explicitly.
- Secrets go in `wrangler secret`, never in source, config, or specs.
- No `any` on `Env` or handler params; use generated and platform types. No `as unknown as T` casts to force type matches.
- Local dev runs in **workerd, not Node** — Node-only APIs require `nodejs_compat`; prefer Web-standard APIs.
- Local D1 data is dev-only scratch: schema changes must be applied to remote explicitly (`pnpm db:migrate:remote`).
- **CPU vs wall (official limits, verified 2026-10-24)**: HTTP requests have
  UNLIMITED wall time while the client stays connected; only CPU time counts
  (waiting on fetch/R2/D1 is free), capped by `limits.cpu_ms` (we set the 5-min
  maximum). Heavy work streams; never assume a wall-clock bound on request
  handlers. `ctx.waitUntil` extends only 30 s past the response — sub-second
  tasks only. **Cron triggers with intervals < 1 h get only 30 s CPU** (15 min
  wall only for ≥1 h intervals); queue consumers get 15 min wall + the CPU
  limit per invocation — crons enqueue, consumers do the work.

### Local dev & CI environment

- GitHub runner-images deliberately alias localhost → ::1, and vite binds ::1
  ONLY — every dev-server poll MUST dial the explicit bind
  (`pnpm dev --host 127.0.0.1`); fast connection refusals are a bind-family
  mismatch, not a slow boot (actions/runner-images#929/#10061, 05bcd56).
- The vite plugin NEVER applies D1 migrations (`migrations_dir` is
  wrangler-CLI-only, verified in the plugin dist) — every CI/dev flow that
  boots a worker against fresh state runs `pnpm db:migrate:local` first, else
  the first metadata write 500s "no such table" (34b4a52).
- URLPattern (the engine router uses it) ships in workerd and Node ≥ 24 only —
  plain-Node tooling whose bundle reaches it dies on the old floor
  ("URLPattern is not defined"); this is the engines floor's reason (28c71ce).
- `actions/upload-artifact` needs `include-hidden-files: true` for
  dot-directories — without it `.full-suite-gate/` evidence never uploaded and
  every red run lost its error text (62a2e92).

## Deploy Discipline

- `wrangler deploy` ships `dist/`'s GENERATED config — any vars/routes change
  REQUIRES `pnpm build` first; the deploy output's var table is the tell for a
  stale dist (the placeholder-id deploy failure, `docs/ops/runbook.md`).
- A deployment preserves the on-disk posture: the demo-flip rides the committed
  config through build+deploy; `.dev.vars` pins keep LOCAL tests in the
  self-host posture — the vitest plugin injects wrangler VARS into test envs,
  so a locally flipped config arms demo goldens on its own (ADR-0005 D3).

## Upstream-Parity Decision Rule

**Upstream behavior IS the default decision.** When upstream Gitea has an
answer (an architecture, a protocol, a posture), implementing it faithfully is
not a decision point — proceed and record it in the SPEC; never ask the user.
Ask only when (a) upstream itself has no answer for the surface, or (b) the
Workers platform makes upstream's shape impossible and MULTIPLE equally
upstream-faithful adaptations exist. Learned 2026-10-29 (the SPEC-0012
"external runner decision" that wasn't one: upstream's own architecture puts
execution outside the server — the control plane is pure parity work).

## Gitea Compatibility References

When implementing or reviewing an API endpoint, check upstream behavior in the submodule:

- OpenAPI spec (authoritative API surface): `gitea/templates/swagger/v1-swagger.generated.json` (also `v1-openapi3.generated.json`).
- Route implementations: `gitea/routers/api/v1/`.
- Request/response structs: `gitea/modules/structs/`.

API responses (field names, error shapes, status codes) should match upstream Gitea behavior; document intentional divergences in the relevant SPEC.
