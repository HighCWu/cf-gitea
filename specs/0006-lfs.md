# SPEC-0006: Git LFS (batch API v1 on R2, presigned checksum-bound hrefs)

Status: draft · Date: 2026-10-24 · Implements ADR-0001 D3 (R2 allocation for LFS,
"checksum-bound presigned PUTs") and D2 (the LFS wire protocol is part of the Tier-1
git contract every git-lfs client exercises). Upstream reference: submodule pin
`fc49368845` (v29.0.0-dev-208; ADR-0001 D5). All file citations below are from that
pin.
References: `specs/0001-storage-engine.md` (engine, object index), `specs/0002-auth.md`
(credentials, scopes), `specs/0003-repo-lifecycle-git-http.md` (route adapter, ACL
matrix, delete purge, §6 presign open question), `specs/0004-api-v1-core.md` §2.4
(the `GET /repos/{o}/{r}/media/{filepath}` tier-1 row this SPEC completes),
`docs/research/tech-route-survey.md` §"Design patterns worth adopting" (gitorange LFS
presign pattern).

## 1. Problem and scope

git-lfs stores large file *content* out of band: the git repo holds a small text
pointer (oid + size), and a separate HTTP API moves the bytes. cf-gitea must speak
that protocol (`{repo}.git/info/lfs/*`) or every real-world repo with binaries fails
to clone/push correctly. Content lives in R2 (ADR-0001 D3), so the LFS server is a
Worker route family over R2 + D1 — no engine changes.

In scope:

- LFS batch API v1 (`POST …/info/lfs/objects/batch`), upload (`PUT objects/{oid}/{size}`),
  download (`GET objects/{oid}` / `objects/{oid}/{filename}`), and verify
  (`POST verify`) — exact upstream wire shapes (§2).
- Href strategy: short-lived presigned R2 URLs with the sha256 checksum bound into
  the signature (gitorange pattern) as the default; Worker-relayed streaming as the
  always-available fallback (§2.3).
- Pointer format library (parse/generate/validate), shared with the SPEC-0004
  `media/`, `git/blobs`, and `contents` LFS enrichments (§2.6).
- R2 key layout, D1 `lfs_objects` state machine, integrity model, size limits,
  quota (§3, §4).
- Retention: stale-`uploading` sweep + reachability GC; repo-delete purge wiring into
  the SPEC-0003 §2.5.5 queue (§3.4).
- Optional receive-time gate rejecting pushes whose new pointers have no uploaded
  objects (§2.5) — upstream has no such gate; ours is config-gated off by default.
- LFS file locks (`info/lfs/locks/*`) — landed (§2.7, 2026-10-30).

Out of scope: SSH/pure-SSH LFS transfer and the LFS JWT machinery tied to it (§2.4:
no SSH exists on Workers — documented exclusion, like SPEC-0003's SSH note); the
`transfers` negotiation beyond `basic` (upstream also only implements basic);
`git lfs migrate`-style server help (client-side); wiki LFS (wikis excluded per
SPEC-0003); repo mirroring with LFS download (upstream `StoreMissingLfsObjectsInRepository`
is mirror-only, mirrors are deferred per ADR-0001); admin LFS settings surface
(tier 3).

## 2. API surface

### 2.1 Route table

Upstream registers the whole family under one group with `m.Any("/*", NotFound)`
catch-all (`gitea/routers/common/lfs.go:15-31`), wired into the web router at
`routers/web/web.go:1777` behind middlewares: `lfsServerEnabled` (plain 404 when
`LFS_START_SERVER` is false, `routers/web/web.go:402-407`), Basic auth + deploy-token
auth, CORS, sign-in-from-any-origin. The same group is mounted on the internal router
for the SSH path (`routers/private/internal.go:105`). The repo name is resolved after
trimming one `.git` suffix (`services/lfs/server.go:431`).

cf-gitea mounts the identical shapes at `/:owner/:repo(.git)?/info/lfs/*` using the
SPEC-0003 §4.4 `.git` normalization (a repo named `foo` is served at both
`/foo/info/lfs/…` and `/foo.git/info/lfs/…`, no redirect between them), plus the
SPEC-0003 §2.5.3 redirect check on owner/repo:

| Method | Route | Handler | Auth (SPEC-0002 scope × SPEC-0003 ACL) |
|---|---|---|---|
| POST | `/:owner/:repo(.git)?/info/lfs/objects/batch` | batch v1 (§2.2) | `write:repository` when `operation:"upload"`, `read:repository` for `download` |
| PUT | `/:owner/:repo(.git)?/info/lfs/objects/{oid}/{size}` | upload (§2.3) | `write:repository` |
| GET | `/:owner/:repo(.git)?/info/lfs/objects/{oid}` | download (§2.3) | `read:repository` |
| GET | `/:owner/:repo(.git)?/info/lfs/objects/{oid}/{filename}` | download + `Content-Disposition` (filename is base64url, `server.go:176-183`) | `read:repository` |
| POST | `/:owner/:repo(.git)?/info/lfs/verify` | verify (§2.3) | `write:repository` (upstream `getAuthenticatedMeta(…, requireWrite=true)`, `server.go:404`) |
| GET | `…/info/lfs/locks` | locks list (§2.7; `requireSigned` — anonymous 401s even on public repos) | `read:repository` |
| POST | `…/info/lfs/locks` | locks create (§2.7) | `write:repository` |
| POST | `…/info/lfs/locks/verify` | locks verify (§2.7; READ scope + write access — upstream locks.go:216/221) | `read:repository` |
| POST | `…/info/lfs/locks/{lid}/unlock` | locks delete (§2.7) | `write:repository` |
| ANY | `…/info/lfs/*` | 404 catch-all (parity with upstream `lfs.go:29`) | — |

Everything below is served only when LFS is enabled (`lfsServerEnabled` parity:
config-off ⇒ plain `404` for the whole subtree, matching
`tests/integration/api_repo_lfs_test.go:26-40`). Handlers stay thin per AGENTS.md;
the protocol logic lives in `src/services/lfs/`.

### 2.2 Batch API v1 (wire contract)

Content type is `application/vnd.git-lfs+json` for request and response
(`modules/lfs/shared.go:16`). Upstream checks the `Accept` header's first
`;`-segment and answers `415` on mismatch (`CheckAcceptMediaType`,
`services/lfs/server.go:104-112`; pinned by
`tests/integration/api_repo_lfs_test.go:42-52`). JSON decode failure → `400`
(`server.go:194-198`); unknown `operation` → `400` (`server.go:200-210`); object
count over `LFS_MAX_BATCH_SIZE` → `413` (`server.go:219-222`).

Request (`modules/lfs/shared.go:27-32`):

```json
{
  "operation": "upload",
  "transfers": ["basic"],
  "ref": {"name": "refs/heads/main"},
  "objects": [{"oid": "<64 lowercase hex>", "size": 12345}]
}
```

`transfers` and `ref` are accepted and ignored (upstream never reads them in
`BatchHandler`; it always answers with basic-transfer semantics). Per-object
results are returned even for invalid objects — the envelope is `200` with
per-object `error` blocks, never a whole-request failure for object-level problems
(pinned by `tests/integration/api_repo_lfs_test.go:100-146`).

Response (`shared.go:49-67`; upstream emits no `transfer` field and no `hash_algo`
— git-lfs defaults to basic, `modules/lfs/http_client.go:108-112`):

```json
{
  "objects": [
    {
      "oid": "…", "size": 12345,
      "actions": {
        "upload": {"href": "…", "header": {"x-amz-checksum-sha256": "…"},
                   "expires_at": "2026-10-24T12:45:00Z", "expires_in": 900},
        "verify": {"href": "…", "header": {"Authorization": "…"}}
      },
      "error": {"code": 404, "message": "Not Found"}
    }
  ]
}
```

Per-object semantics ported from `server.go:228-293`:

| Condition (upload op) | Response object |
|---|---|
| oid not 64-hex or size < 0 (`Pointer.IsValid`, `modules/lfs/pointer.go:98-106`) | `error {422, "Oid or size are invalid"}`, no actions |
| row exists and `size` differs from row | `error {422, "Object <oid> is not <size> bytes"}` |
| size > `LFS_MAX_FILE_SIZE` and object not yet stored | `error {422, "Size must be less than or equal to <max>"}` |
| row exists (`verified`) **or** adopt succeeds (§3.3) | no `actions` — git-lfs treats empty actions as "already present" (`http_client.go:184-187`) |
| otherwise | `upload` href (+ checksum header, §2.3) and `verify` href |

| Condition (download op) | Response object |
|---|---|
| invalid pointer | `error {422, "Oid or size are invalid"}` |
| size mismatch vs row | `error {422, "Object <oid> is not <size> bytes"}` |
| no `verified` row or object missing in R2 | `error {404, "Not Found"}` (batch-spec code semantics, `shared.go:90-102`) |
| otherwise | `download` href only |

Error responses outside the batch envelope carry the LFS media type and a JSON body
`{"message": "<status text>"}` (upstream `writeStatusMessage`, `server.go:530-540`).

Nonexistent repo → `404` **before** any auth challenge; repo exists but the caller
cannot access it (or sends no credentials) → `401` +
`WWW-Authenticate: Basic realm="gitea-lfs"`; authenticated but the token lacks the
`read:`/`write:repository` scope → `403`. This is exactly upstream's split
(`getAuthenticatedRepository` → repo lookup 404 at `server.go:462-468`,
`authenticate`/`requireAuth` 401 at `server.go:470-473, 632-635`,
`CheckRepoScopedToken` 403 at `server.go:475-483`). Note this intentionally
**diverges** from SPEC-0003 §2.4's anti-enumeration 404 rule for existing-but-hidden
repos: upstream's LFS routes challenge (`401`) where its git-HTTP routes 404, and we
keep upstream's wire behavior here (the repo's existence is not disclosed — the
challenge is issued regardless).

### 2.3 Href strategy — decision: checksum-bound presigned R2 URLs, relay fallback

Upstream's HTTP hrefs point back at Gitea itself with the caller's `Authorization`
header echoed into the Link (`server.go:488-524`); when the LFS storage backend is
S3-compatible and `ServeDirect` is on, upstream instead hands out a presigned GET
and drops the auth header (`server.go:496-503`, `routers/api/v1/repo/file.go:186-192`,
`routers/web/repo/download.go:48-55`). cf-gitea makes the presigned form the
**default for both directions** (gitorange pattern,
`docs/research/tech-route-survey.md`: "LFS via pre-signed R2 PUT with the checksum
bound into the signature (`x-amz-checksum-sha256 = oid`), D1 stores bare keys only"):

- **Upload href** = presigned R2 `PUT` of `lfs/<storage_key>/<oid>` with
  `x-amz-checksum-sha256` (base64 of the oid's raw 32 bytes) bound into the
  signature *and* repeated in the Link's `header` map so git-lfs sends it
  (gitorange `worker/src/lib/lfs.ts:31-77`, `worker/src/lfs-http.ts:184-196`). R2
  validates the header against the payload and stores the checksum, so **a successful
  PUT proves sha256(content) == oid** — integrity is enforced by storage, not by a
  later pass. The client can compute the header value from the oid alone (no content
  pass needed). git-lfs basic upload sets a concrete `Content-Length`
  (`transferadapter.go:60`), so no chunked-signing problems arise.
- **Download href** = presigned R2 `GET` with optional `response-content-disposition`
  / `response-content-type` overrides signed in (filename support parity with
  upstream `objects/{oid}/{filename}`; gitorange `lfs.ts:61-69`). `Range` resume
  works natively via S3 semantics (upstream hand-parses `Range`,
  `server.go:114-151` — code we do not need in presign mode).
- **Verify href** = our own `POST …/info/lfs/verify` with the caller's
  `Authorization` echoed (upstream shape, `server.go:518-520`) — the one hop that
  stays on the Worker, because it flips D1 state.
- TTL: `X-Amz-Expires` = `LFS_URL_TTL_SECONDS` (default 900); Link objects carry
  both `expires_at` (RFC3339) and `expires_in` so git-lfs can refresh by re-batching.
- Signing uses S3 credentials (`R2_ACCESS_KEY_ID` / `R2_SECRET_ACCESS_KEY` wrangler
  secrets + account id var) with SigV4 query presigning via `aws4fetch` (the only
  new runtime dependency; gitorange-proven). The R2 **binding does not expose
  presigning** — `createPresignedUrl` is not part of the binding API; presigned URLs
  require S3 credentials + local SigV4 computation. This is the same open question
  SPEC-0003 §6 records for the import channel; this SPEC resolves its half as
  "S3-credential presign, never undocumented binding APIs", and SPEC-0003 §2.6
  should share the one signer util. Presigning is pure local HMAC — zero subrequests.

**Fallback (mandatory to implement): Worker-relayed streaming**, selected when the
S3 credentials are absent or `LFS_HREF_MODE=relay` is configured. hrefs then point
at the Worker with upstream's exact shapes: upload `PUT objects/{oid}/{size}` with
`Authorization` echo + the `Transfer-Encoding: chunked` hint (`server.go:510-515`);
download `GET objects/{oid}[/{filename}]` with `Authorization` echo
(`server.go:504-507`). Relay upload streams `request.body` once through a
single-pass hash-and-forward transform (each chunk enqueued downstream **and**
written into a `crypto.subtle` DigestStream — never `.tee()`, which buffers the
unconsumed branch in isolate memory) into R2 via the storage service layer, with
`FixedLengthStream` when Content-Length is known (SPEC-0001 §5 discipline; AGENTS.md
streaming rule). Mismatch or size violation ⇒ delete the R2 object, `422` body
`{"message":"…hash does not match OID…"}` (upstream `ErrHashMismatch`/
`ErrSizeMismatch`, `modules/lfs/content_store.go:18-23`, hashingReader
`:114-165`).

Justification against Workers constraints: LFS objects default to ≤512 MiB; relaying
is legal (streaming, low CPU) but puts every byte through an isolate and re-hashes
it, while presigned PUTs take the Worker off the data path entirely, get R2 to
enforce the oid for free, and cost zero subrequests to mint. Presigned URLs are
bearer credentials — mitigated by the 15-minute TTL and per-object key scope (a
leaked URL exposes one object of one repo, read or overwrite-once). Relay mode
exists because it needs no secrets (day-one local dev, and deployments that do not
mint R2 API tokens) and because it is upstream's wire shape verbatim — the
compatibility escape hatch. Both modes sit behind one `LfsStore` capability
interface (`presignPut/presignGet` return `null` when unsupported ⇒ callers use the
relay handlers), so SPEC-0003 §6's binding-presign question can flip the default
without touching handlers.

Auth on the batch/verify endpoints: git-lfs always sends HTTP Basic from git
credentials; upstream mounts exactly Basic + deploy-token auth on these routes
(`web.go:1777` `AllowBasic`, `AllowDeployToken` — notably *not* OAuth2/session).
cf-gitea: Basic only, parsed per SPEC-0002 §2 (token as password; token as username
with empty password), resolved to a principal, then the scope + ACL checks of §2.2.
There is **no LFS JWT in cf-gitea**: upstream's HS256 JWT (`Claims{RepoID, Op, …}`,
`server.go:50-86, 577-630`, secret `LFS_JWT_SECRET`, expiry `LFS_HTTP_AUTH_EXPIRY`
default 24 h, `modules/setting/lfs.go:17-27, 63-84`) exists to carry authorization
into hrefs on the pure-SSH transfer path (`LFS_ALLOW_PURE_SSH`,
`tests/integration/git_lfs_ssh_test.go`); SSH does not exist on Workers, and our
hrefs are self-authorizing (presign) or echo the caller's own header (relay), so the
token machinery is dead weight. Documented exclusion.

Upload handler (relay mode), ported from `server.go:306-392`: validate
pointer-from-path (`oid`, integer `size`) → `422` when invalid; write auth; if R2
already holds the object **and** a row exists for this repo, skip the body check
(upstream `server.go:328-339`); if R2 holds it but no row exists, upstream
re-reads and re-hashes the body as proof of possession (deploy-key cross-repo
protection, `server.go:339-358`) — cf-gitea keeps the re-hash (defense in depth)
even though per-repo keys already make cross-repo adoption impossible (§3.1);
then insert/refresh the `lfs_objects` row (`NewLFSMetaObject` insert-if-absent
semantics, `models/git/lfs.go:106-119`). `200` with empty body on success
(upstream `writeStatus(200)`).

Verify handler, ported from `server.go:395-420` + `content_store.go:95-106`: JSON
`{"oid", "size"}`; write auth; presign mode ⇒ `HEAD` the key, require `size`
match **and** stored checksum == oid; relay mode ⇒ existence + size (identical to
upstream, whose hash was enforced at Put time). `200` `{"message":"OK"}` /
`404` `{"message":"Not Found"}` / `500` on store errors. On success the row flips
`uploading → verified`.

Download handler (relay mode), ported from `server.go:117-189`: row lookup (404),
stream the R2 GET body with `Content-Type: application/octet-stream`,
`Content-Length` + upstream's `X-Gitea-LFS-Content-Length` parity header
(`server.go:172-173`), `Content-Disposition` from the base64url `{filename}`
segment, `Range` → `206`/`416` (only in relay mode; presigned GETs inherit S3
range semantics and skip the parity header — accepted divergence, it exists to
protect against reverse proxies mangling lengths, which does not apply to a
direct R2 response).

### 2.4 Pointer format

Spec v1 (`modules/lfs/pointer.go:20-27`): pointer files are `< 1024` bytes
(`MetaFileMaxSize`), first line exactly `version https://git-lfs.github.com/spec/v1`,
then `oid sha256:<64 lowercase hex>` and `size <n>` (parser `pointer.go:53-80`:
prefix check, ≥3 lines, strict 64-lowercase-hex oid `:82-94`, non-negative size;
canonical serialization `StringContent()` `:110-112` — key/value order fixed, so
pointer bytes are reproducible). cf-gitea ports this as a dependency-free module
(`src/services/lfs/pointer.ts`) with the same three error classes
(`ErrMissingPrefix`/`ErrInvalidStructure`/`ErrInvalidOIDFormat`) and strict parse
(no `parseInt` leniency — same discipline as SPEC-0001 §7 pkt-line parsing).
`git/blobs`/`contents` LFS enrichment and the receive-time gate (§2.5) share this one
parser; anything that is not a valid pointer is treated as ordinary content
everywhere.

### 2.5 Push-path integration

Pointers inside pushed packs are **just blobs — zero engine changes** (SPEC-0001 is
LFS-unaware by design). Upstream likewise never inspects pushes for pointers: the
git-lfs client's pre-push hook uploads objects *before* `git push`, and upstream's
only pointer scanning is offline (`SearchPointerBlobs`,
`modules/lfs/pointer_scanner.go:23-57` — `cat-file --batch-check` filtered to blobs
< 1024 bytes), used by mirror sync (`modules/repository/repo.go:61-167`) and the
doctor (`services/doctor/lfs.go`). A push containing pointers whose objects were
never uploaded lands fine, and every read path falls back to serving the pointer
text (`routers/api/v1/repo/file.go:145-151`, `routers/web/repo/download.go:40-43`).

cf-gitea adds an **optional receive-time gate** (config
`lfs.reject_missing_objects_on_push`, default **off** = upstream-faithful): during
the SPEC-0001 §5 receive pass-1 scan, every blob entry with size ≤ 1024 is inflated
(bounded — a 1 KiB window, negligible against the T2 budget) and pointer-parsed;
after pass-2 indexing and **before** the `finalizeReceive` CAS, the gate requires
every collected oid to have a `verified` row (single chunked D1 `IN` query), else
the push fails with a sideband fatal message naming the first missing oid — no refs
touched, staging swept. Placement note: this is a *pre-finalize* gate, not a
post-receive rollback — upstream expresses the same semantics with a pre-receive
hook (client sees a declined push), and post-receive ref rollback would race
subsequent pushes and break the atomic-ref-commit invariant (SPEC-0001 §5). Reading
the just-built pack index keeps the check O(new blobs ≤1 KiB).

### 2.6 Interplay with SPEC-0004 tier-1 routes

- `GET /repos/{o}/{r}/media/{filepath}` (SPEC-0004 §2.4 row): resolution algorithm
  ported from `GetRawFileOrLFS` (`routers/api/v1/repo/file.go:90-201`): empty repo
  → 404; blob > 1024 bytes → serve blob bytes (ETag-cached); else parse pointer;
  invalid pointer → serve the ≤1 KiB content; valid pointer with **no** `verified`
  row → serve the pointer text itself (upstream `:145-151` — clients see the
  pointer, which is the truthful representation of an un-uploaded object); valid
  pointer with row → ETag on `oid` + `updated_at` (`:167-172`), then **302 redirect
  to the presigned GET** (presign mode; upstream ServeDirect behavior `:186-192`,
  filename and `Content-Disposition` signed into the URL) or inline relay stream
  with `Content-Disposition` (relay mode). `ref` resolution rules (query param +
  `{ref}/{filepath}` legacy form) are SPEC-0004 §4's, unchanged.
- `GET …/raw/{filepath}` never LFS-resolves — pointer text is the raw content
  (upstream `SingleDownload` uses `common.ServeBlob`, `download.go:96-109`).
- `GET …/git/blobs/{sha}` and `GET …/contents[/{filepath}]` add upstream's
  `lfs_oid` / `lfs_size` enrichment when the blob parses as a pointer
  (`services/repository/files/content.go:250-265`; swagger properties
  `lfs_oid`/`lfs_size`) — SPEC-0004 already pins these fields; this SPEC supplies
  the parser and the row lookup (size from the row when present, else the pointer's
  declared size).
- Repo delete: the SPEC-0003 §2.5.5 queue purge message gains one prefix — the
  consumer deletes `lfs/<storage_key>/` alongside `repos/<storage_key>/` and
  `imports/<storage_key>/` (paged list + batch delete, idempotent under redelivery).
  No D1 cascade needed: the repo row deletion (§2.5.5 step 1) removes
  `lfs_objects` rows in the same transaction.
- Rename/transfer: nothing (keys are `storage_key`-addressed).
- Forks: **LFS metadata is not copied** — divergence from upstream, whose global
  content store makes `CopyLFS` a pure D1 row copy (`models/git/lfs.go:256-271`).
  With per-repo R2 keys, copying rows would reference the parent's prefix. Fork
  users recover with `git lfs fetch --all && git lfs push --all`; re-uploads are
  cheap because batch adopt (§3.3) skips already-present objects. (R2 Batch Copy in
  the fork queue is a recorded follow-up, §6.)

### 2.7 Locks

**LANDED 2026-10-30** (migration 0045, `src/services/lfs/locks.ts` +
`src/lfs/locks.ts`). Upstream implements the file-locking API at
`info/lfs/locks{,/verify,/{lid}/unlock}` (`routers/common/lfs.go:23-28`, handlers
`services/lfs/locks.go`, model `models/git/lfs_lock.go`) — needed only when a user
runs `git lfs lock`/`unlock`; push/pull never touch it. One D1 table (`lfs_locks`:
upstream columns id/repo_id/owner_id/path/created_at, PLUS a `lower_path` copy
carrying a UNIQUE `(repo_id, lower_path)` index — upstream enforces the
case-insensitive per-repo uniqueness with an in-transaction SELECT
(`lfs_lock.go:74-80`); D1 has no check-then-insert transaction, so the folded
column turns the create race into a conflict → 409 with the existing lock echoed,
wire-invisible). `repo_id` uses the §2.1 numeric bridge.

Routes and arms, upstream-exact at the pin:

- The four registrations sit in a group carrying `CheckAcceptMediaType`
  (`lfs.go:28`): a MATCHED route 415s (`{"message":"Unsupported Media Type"}`,
  LFS media type) before auth; a method mismatch (GET `locks/verify`,
  DELETE `locks`, …) falls to the family catch-all's plain-text 404.
- Auth per verb (locks.go:62/151/216/284): list/verify check the READ scope,
  create/unlock the WRITE scope; `authenticate` requires a signed-in doer for
  ALL four (`requireSigned=true`) with write access for create/verify/unlock —
  so anonymous requests 401 even on public repos, and a read-scope token of a
  writer CAN verify (upstream's own asymmetry). No-grant → 401 with the
  route-specific message ("You must have pull access to list locks" / "You must
  have push access to {create,verify,delete} locks") + the gitea-lfs realm; the
  §2.2 family posture (disabled/owner-prohibited 403s, archived-write 403) is
  kept.
- Create: body decode failure → `writeStatus(400)`; absent `path` decodes as ""
  and is creatable (upstream validates nothing); 201 `{"lock":{...}}`;
  duplicate → 409 `{"message":"already created lock","lock":<existing>}` —
  `CreateLFSLock` returns the FOUND row on conflict. Paths are
  `util.PathJoinRel`-normalized and matched case-insensitively (the upstream
  integration test's `"Foo/BaR.zip"` and dot-segment fixtures conflict).
- List: `?id=` arm (Go `strconv.ParseInt` failure → 400 `"bad request : " +
  err.Error()` with the Go error text), `?path=` arm (single case-insensitive
  match or `{"locks":[]}`), else paged: `cursor` is a PAGE number over `limit`
  rows ordered by id — cursor 0 and 1 alias the first page (upstream quirk,
  `(page-1)*pageSize` at `lfs_lock.go:117-128`); `limit` caps at
  `LFS_LOCKS_PAGING_NUM` (50, `modules/setting/lfs.go:50-52`); `limit <= 0`
  (incl. missing/non-numeric) means UNLIMITED; `next_cursor` rides only when
  the page came back full.
- Verify: same paging, rows split `ours`/`theirs` by `owner_id == doer.id`.
- Unlock: `PathParamInt64` discards the parse error (syntax → 0); body decodes
  `{force}` (failure → the writeStatus 400 arm). Upstream maps EVERY
  `DeleteLFSLockByID` error to ONE arm (locks.go:311-318): 500 `"unable to
  delete lock : Internal Server Error"` — that includes lock-not-found AND
  not-owner-without-force (`lfs_lock.go:161-163`); there is NO 404/403 arm at
  this pin. `force: true` lets any writer remove another user's lock. Success
  echoes the deleted lock (200).
- Wire bytes: upstream's `ctx.JSON` sets `application/json;charset=utf-8` AFTER
  the handlers set the LFS media type (so it wins) and the pin's jsonv2 encoder
  (`modules/json/jsonv2.go`) routes `Encoder.Encode` AND `MarshalWrite` to the
  same compact `MarshalWrite` — verified empirically — so every locks body is
  compact JSON WITHOUT a trailing newline. (The batch/upload/verify
  `writeStatus` envelopes in §2.2-§2.3 are emitted through the same code path
  at this pin; their shipped `"\n"` suffix is a recorded cosmetic divergence to
  reconcile family-wide.) `locked_at` renders second-rounded RFC3339
  (`convert.ToLFSLock`); the wire lock `id` is the decimal string of the row id.

## 3. Data model

### 3.1 R2 keys

```
lfs/<storage_key>/<oid>        # one object per repo per oid; single-shot PUT only
```

`storage_key` is the immutable `r_<id>` (SPEC-0003 §3.1) — **no name-derived keys**;
`oid` is the validated 64-hex sha256, so the key is content-addressed and
injection-proof (invalid oids never reach key construction; upstream's panic guard
`pointer.go:115-124` ports as a 500-avoiding precondition). Divergence from
upstream, which stores one global copy per oid (`oid[0:2]/oid[2:4]/oid[4:]`,
`pointer.go:115-124`) shared by all repos: per-repo keys duplicate bytes across
repos (R2 at $0.015/GB-mo — acceptable) but make repo deletion a pure prefix purge,
eliminate upstream's cross-repo refcounting on delete
(`RemoveLFSMetaObjectByOidFn` count check, `models/git/lfs.go:146-170`) and the
global-store orphan sweep. Bucket: the same R2 bucket as SPEC-0001/0003 (single
binding; `lfs/` prefix), with a dedicated-bucket override as config-only
alternative (the presign URL carries the bucket name). Size envelope: single-shot
PUT only — git-lfs's basic adapter has no multipart (`transferadapter.go:49-68`),
R2's single-PUT ceiling is 5 GiB ⇒ no multipart staging keys, no partial-upload
sweeping, and concurrent same-key PUTs are atomic last-write-wins of **identical**
content (both checksum-bound to the same oid).

### 3.2 D1 (addition; migration via drizzle-kit)

`lfs_objects` — **bare keys only** (the R2 key is the pure function
`lfs/<storage_key>/<oid>`, never stored):

| column | type / notes |
|---|---|
| `repo_id` | → repositories.id, PK part |
| `oid` | text 64-hex, PK part — `PRIMARY KEY (repo_id, oid)` (upstream `UNIQUE(s)`, `models/git/lfs.go:83`) |
| `size` | integer (declared size; checked against stored object at verify/adopt) |
| `state` | `'uploading' \| 'verified'` |
| `created_at`, `updated_at` | timestamps (`updated_at` feeds GC grace and media ETags, like upstream `UpdatedUnix`, `models/git/lfs.go:85-86`) |

Indexes: `(repo_id, state, updated_at)` (sweeps); the PK covers batch lookups.
Batch oid lookups chunk the `IN` list at ≤90 binds (D1 bind cap). No row is created
for a pointer merely seen in git history — rows exist only for objects the LFS API
touched, exactly like upstream's `lfs_meta_object`.

`repositories.lfs_size`: computed on read (`SELECT SUM(size) … state='verified'`)
for the swagger `Repository.lfs_size` / `repos/search` `lfs_size` sort (SPEC-0004);
not a maintained column at this tier.

### 3.3 `lfs_objects` state machine

```
        batch(upload)                     R2 PUT (presigned)      verify(200)
(absent) ────────────▶ uploading ────────────────────────────▶ verified
                          │  ▲                                    │
                          │  └── batch(upload) re-issues href     │ batch(upload):
                          │      after failure/expiry             │ row present ⇒ no actions
                          ▼                                       │
                        (sweep: >24 h) ── HEAD ok ──────▶ verified│
                          │                                       │
                          └─ HEAD missing ⇒ row deleted ◀─────────┘
                                                    (GC: unreachable > grace ⇒ row+object deleted)
```

- **Adopt** (batch upload/download, and verify): if no row exists but `HEAD
  lfs/<key>/<oid>` matches declared size **and** (presign mode) stored
  `checksums.sha256` hex == oid, insert the row as `verified` instead of re-uploading
  (gitorange `adopt`, `worker/src/lfs-http.ts:139-156`; covers "upload finished,
  verify never arrived"). This is safe because the key is repo-scoped: only bytes
  authorized for *this* repo can be there.
- **Idempotent upload**: batch when a `verified` row exists (or adopt succeeds) ⇒
  no `actions` — the client skips the transfer (`http_client.go:184-187`).
- **Re-upload after failed verify**: row stays `uploading`; a fresh batch re-issues
  a fresh presigned PUT (new signature, new expiry). No cleanup needed — the next
  successful PUT overwrites the same key atomically.

### 3.4 Sweeps and GC (Queue + cron)

- **Stale-`uploading` sweep**: cron trigger → one Queue message per repo having
  `state='uploading' AND updated_at < now-24h`; consumer `HEAD`s each key
  (budgeted, `waitUntil`; queue redelivery on failure): validates ⇒ promote
  `verified`; missing ⇒ delete row. (With single-shot PUTs there is no partial
  object to reap.)
- **Reachability GC** (upstream `GarbageCollectLFSMetaObjects`,
  `services/repository/lfs.go:33-146`, a weekly-grace cron): for `verified` rows
  with `created_at` and `updated_at` older than `LFS_GC_GRACE` (default 7 d —
  upstream's guard against upload/push ordering races, `lfs.go:120-131`): compute
  the pointer blob's git sha1 (`sha1("blob <len>\0" + canonical pointer text)`,
  upstream `ComputeBlobHash`, `lfs.go:92`) and ask the RepoDO object index
  (`hasBlob` RPC, SPEC-0001 §4 index rows) whether it exists. Missing ⇒ delete the
  row **and** the R2 object (per-repo keys ⇒ no refcounting). Paged iteration, one
  repo per Queue message.
- **Repo delete purge**: §2.6 / SPEC-0003 §2.5.5 step 3 (prefix `lfs/<storage_key>/`).

## 4. Edge cases, limits, failure modes

| # | Case | Behavior |
|---|---|---|
| 4.1 | **Concurrent uploads, same oid** | Presigned PUTs race on one key; each is atomic and checksum-bound to the same oid ⇒ final state is one complete, correct object regardless of order. Relay mode: same key, single-PUT atomicity, identical bytes. Both requests may verify successfully. |
| 4.2 | **Re-upload after failed verify** | Row remains `uploading`; batch re-issues hrefs. Stale `uploading` rows are swept (§3.4); R2 garbage from never-verified uploads is unreachable-by-row and reclaimed by GC grace or delete purge. |
| 4.3 | **oid collision** | Treated as impossible: oid *is* the sha256 of the content and the storage key; a collision would break git itself. No runtime check beyond format + checksum match. |
| 4.4 | **Pointers pushed without objects** (foreign pushes, LFS bypass) | Gate off (default): push lands; pointer text is served by raw/media/contents as ordinary content; batch download for that oid → per-object `404`; media → pointer text (§2.6). Gate on (§2.5): push rejected pre-finalize with sideband error naming the missing oid. |
| 4.5 | **Presigned URL expires mid-operation** | Client PUT/GET after expiry → `403` (S3 `SignatureDoesNotMatch`-class error); git-lfs honors `expires_at`/`expires_in`, re-batches, and retries with fresh hrefs. Batch re-issue is stateless (§3.3). |
| 4.6 | **Oversize object** | Batch: per-object `422` "Size must be less than or equal to …" (upstream string, `server.go:273-278`) before any href is issued. Relay PUT with lying Content-Length or runaway body: `FixedLengthStream`/counting transform aborts, object deleted, `422`. Limits: default 512 MiB (`LFS_MAX_FILE_SIZE`, configurable; upstream default is unlimited/0, `modules/setting/lfs.go:22`), hard cap 5 GiB (R2 single PUT; gitorange's cap, `worker/src/lib/lfs.ts:5`). |
| 4.7 | **Quota** | Per-repo `lfs_objects` projected sum + new size > `LFS_REPO_QUOTA` (default 10 GiB) ⇒ per-object `422` "LFS quota exceeded for repository" (our addition — upstream has no per-repo LFS quota; divergence documented). Exercised in e2e T7. |
| 4.8 | **Batch of mixed valid/invalid objects** | Envelope `200`, per-object results, invalid objects never block valid ones (upstream loops per object, `server.go:228-293`; pinned by `api_repo_lfs_test.go:100-146`). |
| 4.9 | **Media type / body hygiene** | `Accept` without the LFS media type → `415` (batch + verify only, upstream `CheckAcceptMediaType`); malformed JSON → `400`; catch-all path → `404`. Error bodies are `{"message"}` with the LFS media type (§2.2). |
| 4.10 | **Object in R2, row missing** (crash between PUT and verify, or verify lost) | Adopt on next batch/verify (§3.3); media serves it only after a row exists. |
| 4.11 | **Archived repo** | LFS writes (upload batch, upload, verify, lock mutation) → `403` (platform-consistent with SPEC-0003 §2.4 row 10; upstream's LFS routes happen not to check archived — minor, safer divergence). Reads unaffected. |
| 4.12 | **Upload path traversal / bad oid** | oid format-gated before key construction (`pointer.go` port); `404` catch-all covers junk paths; no handler ever builds a key from a non-validated segment. |
| 4.13 | **D1 outages mid-batch** | Batch is read-then-write per object; a D1 failure after href issuance leaves at most an `uploading` row + unadopted object — both self-heal (sweep/adopt). Verify is the only state flip and is idempotent. |
| 4.14 | **`{filename}` download param** | base64url-decoded; invalid base64 → param ignored (upstream `server.go:176-183` silently skips on decode error), never reflected raw. |

Unit (`vitest`, workerd pool):

- Pointer module: golden valid pointers, canonical serialization roundtrip, strict

  size, > 1024 bytes), fuzz corpus (truncated/mutated pointers — no throw, boolean
  validity only).

  `x-amz-checksum-sha256` value == base64(hex2bin(oid)), TTL math, response-content

- Batch routing matrix: 400/413/415 + per-object error table (§2.2) — port the
  expectations of `tests/integration/api_repo_lfs_test.go` (InvalidJsonRequest,
  InvalidOperation, InvalidPointer, PointerSizeMismatch, Download PointerNotInStore).
- ACL matrix: anonymous/public (download ok, upload 401), private-no-grant (401
  challenge per §2.2), wrong-scope token (403), nonexistent repo (404 before auth),
  disabled LFS (404 subtree) — upstream `TestAPILFSNotStarted`/`MediaType` parity.

Worker integration (real local D1/R2 via `@cloudflare/vitest-pool-workers`):

- Full state machine: batch(upload) → relay PUT (hash ok / hash mismatch ⇒ object
  deleted + 422 / size lie ⇒ abort) → verify 200 → row `verified`; verify 404 paths;
  adopt (skip verify, re-batch ⇒ no actions); concurrent PUTs both verify; quota and
  max-size rejections; presign mode exercised against a stubbed signer with the same
  handler code path (mode swap via config).
- media/raw/git-blobs/contents interplay: pointer-with-object → 302 (presign) /
  inline (relay); pointer-without-object → pointer text; non-pointer ≤1 KiB file
  served as content; `lfs_oid`/`lfs_size` enrichment.
- Sweeps: stale-`uploading` promote/delete; GC deletes row+object only past grace
  and only when RepoDO `hasBlob` says the pointer blob is gone; delete-purge removes
  `lfs/<storage_key>/` (queue redelivery idempotent).
- Optional push gate: push with missing object rejected pre-finalize (refs
  untouched), accepted once object uploaded; gate-off default untouched.

Black-box e2e with the real `git-lfs` client (CI installs git-lfs):

1. `git lfs track "*.bin"` → commit 100 MB pointer → `git push`: objects uploaded
   (assert R2 key + `verified` row), git push lands.
2. Fresh clone with smudge: object downloaded via presigned GET, bytes identical
   (`git lfs fsck` clean).
3. `git lfs push` / `git lfs fsck` verify path; expired-TTL retry (force `expires_in: 1`
   fixture) re-batches transparently.
4. Upload without prior batch (raw PUT) → 422; wrong-scope token → 403;
   quota exhaustion → client-visible `422` error object with our message.
5. Fork then `git lfs fetch --all` in the fork → re-upload adopts nothing from the
   parent (per-repo keys), objects land independently.
6. Delete repo → `lfs/<storage_key>/` prefix gone.

Conformance: port upstream integration expectations
(`tests/integration/api_repo_lfs_test.go`, `tests/integration/lfs_getobject_test.go`)
as an automated diff list, same discipline as SPEC-0003 §5 item 11; oracle mode
(ADR-0001 D4) diffs against a real Gitea instance where behavior is undocumented.

## 6. Open questions (resolve at implementation)

- **Presign credentials lifecycle**: R2 S3 API tokens cannot be minted by the
  Worker; operators create them in the dashboard. If Cloudflare ships a binding-level
  presign API (SPEC-0003 §6 tracks this), drop the secrets and flip the default
  behind the `LfsStore` capability interface — handlers unchanged.
- **`hash_algo` in batch responses**: upstream omits it; the LFS batch spec allows
  `"hash_algo": "sha256"`. Default: omit (upstream-faithful); add only if a client
  surfaces a need.
- **Fork LFS copy** (§2.6): R2 Batch Copy cost/latency data decides whether forks
  eventually copy rows+objects in the fork queue; until then "no copy" stands.
- **Quota defaults** (512 MiB / 10 GiB): validate against real forge workloads;
  per-owner (not per-repo) quotas are a tier-3 admin concern.
- **Locks timing** (§2.7): P2 unless the UI-tier SPEC pulls it forward.
